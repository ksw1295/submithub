  * 부제: 버전 관리와 피드백 자동 추적을 결합한 지능형 과제 제출 플랫폼
  * 팀원: 컴퓨터공학과 캡스톤 디자인팀
* **발표 대본 (Script)**:

### Slide 2. 배경 및 문제 정의 (Problem Statement)
* **슬라이드 내용**:
  * 기존 대학 LMS(LINC, Canvas, e-Class)의 한계:
    * 1) "압축파일 하나 덜렁 올리고 끝나는" 블랙박스형 과제 제출
    * 2) 교수가 피드백을 주어도 학생이 다음 버전에 실제로 고쳤는지 일일이 눈으로 대조 불가능
    * 3) 변수명만 바꾼 교묘한 표절 행위 적발 한계
    * 4) 학생 제출 코드를 로컬에서 돌려보다가 바이러스/악성코드에 노출되는 채점의 비효율
* **발표 대본 (Script)**:
  > *"교수님들께서 코딩 과제를 채점하실 때 가장 힘드신 점이 무엇일까요? 학생이 zip 파일 하나 올리면, 다운로드받아 압축 풀고 실행해본 뒤 코멘트를 줍니다. 학생이 수정본을 다시 내면, 이전 파일과 새 파일을 양쪽에 띄워놓고 '내가 지적한 부분을 진짜 고쳤나?'를 눈으로 대조해야 합니다. 기존 LMS는 과제의 '과정'이 아닌 '결과'만 받기 때문입니다. 저희는 생각했습니다. **왜 과제 제출은 Git처럼 버전으로 관리되고, GitHub PR처럼 라인 단위로 피드백을 추적할 수 없을까?**"*

---

### Slide 3. 해결책: SubmitHub (Our Solution)
* **슬라이드 내용**:
  * **"Git처럼 관리되는 과제, PR처럼 추적되는 피드백"**
  * 1) **버전 타임라인 (v1 $\to$ v2 $\to$ v3)**: 제출마다 자동 버전 누적
  * 2) **GitHub 커밋 연동**: 저장소 주소와 브랜치만 넣으면 파일 트리 자동 구축
  * 3) **피드백 자동 추적 (핵심 킬러 기능)**: 교수의 라인 코멘트가 새 버전에서 반영되었는지 시스템이 diff로 자동 판정
  * 4) **Winnowing 표절 검사**: 뼈대 코드를 제외한 실제 코드 유사도 매트릭스 계산
  * 5) **Docker 샌드박스 자동 채점**: 컨테이너 격리 상태에서 안전하게 테스트 케이스 채점
* **발표 대본 (Script)**:
  > *"SubmitHub는 개발자들의 표준 협업 방식을 교육 현장에 최적화했습니다. 학생이 과제를 제출하면 v1, v2 버전으로 차곡차곡 쌓이고, 교수는 브라우저 상에서 원하는 코드 줄에 인라인 피드백을 남깁니다. 학생이 다음 버전을 제출하는 순간, 시스템이 자동으로 diff를 계산하여 '교수님의 지적 사항이 몇 퍼센트 반영되었는지'를 1초 만에 판정해 냅니다."*

---

### Slide 4. 시스템 아키텍처 (System Architecture)
* **슬라이드 내용**:
  * Spring Boot 3.5 + Java 17 LTS 기반의 모듈형 아키텍처
  * 자체 알고리즘 엔진: **Myers Diff 직접 구현**, **Winnowing k-gram 엔진 직접 구현**
  * 보안 인프라: **Docker 격리 컨테이너**, **Spring Security + 전방위 IDOR 방어**
* **발표 대본 (Script)**:
  > *"SubmitHub는 외부 무거운 상용 라이브러리에 의존하지 않고 핵심 알고리즘을 순수 자바로 직접 구현했습니다. 코드 변경점을 정밀하게 추적하기 위해 Myers Diff 알고리즘을 구현했고, 학술 논문 MOSS의 기반 알고리즘인 Winnowing 지문 해싱 엔진을 자체 탑재했습니다. 또한 악성 코드 공격을 원천 차단하기 위해 Docker 컨테이너 격리 샌드박스를 구축했습니다."*

---

### Slide 5. 핵심 기술 1: 피드백 반영 자동 추적 (Feedback Tracking)
* **슬라이드 내용**:
  * 교수의 라인 피드백 위치를 Myers Diff의 변경 편집 그래프(Edit Graph)와 맵핑
  * 새 버전 제출 시:
    * **`반영됨 (REVISED)`**: 지적받은 줄이 실제로 수정되거나 새로운 로직으로 개선됨
    * **`미반영 (PENDING)`**: 지적받은 문제 코드가 새 버전에도 그대로 잔존함
    * **`삭제됨 (DELETED)`**: 불필요한 코드가 삭제 정리됨
  * 과제별 / 학생별 **피드백 반영률(%)** 자동 산출 및 대시보드 시각화
* **발표 대본 (Script)**:
  > *"저희의 가장 독창적인 기술인 피드백 반영 추적 메커니즘입니다. 교수가 v1 코드의 특정 줄에 '예외 처리가 빠졌다'고 코멘트를 달면, 학생이 v2를 제출했을 때 시스템이 diff 알고리즘을 통해 해당 줄의 코드 변경 여부를 역추적합니다. 지적받은 줄이 수정되었다면 '반영됨'으로 전환되며, 학생의 반영률이 100%로 계산됩니다. 교수님은 더 이상 두 파일을 눈으로 일일이 대조하실 필요가 없습니다."*

---

### Slide 6. 핵심 기술 2: Winnowing 기반 표절 검사 (Plagiarism Detection)
* **슬라이드 내용**:
  * 단순 텍스트 비교가 아닌 **구조적 어휘 토큰화**:
    * 변수명 치환, 주석 추가/삭제, 공백 변경, 줄바꿈 꼼수 무력화
  * **교수 뼈대 코드(Baseline Code) 제외 필터링**:
    * 수업에서 공통 제공한 템플릿 코드가 표절로 오인되지 않도록 사전 제거
  * **좌우 2분할(Side-by-side) 매칭 뷰어**: 표절 의심 영역을 시각적으로 나란히 하이라이트
* **발표 대본 (Script)**:
  > *"학생들의 표절은 점점 교묘해집니다. 변수명을 바꾸거나 주석을 달아도 SubmitHub의 Winnowing 엔진은 토큰화와 k-gram 해시 정규화를 거쳐 본질적인 로직 유사도를 잡아냅니다. 특히 교수가 수업 때 배포한 뼈대 코드는 표절 검사 대상에서 자동으로 제외되므로, 정밀한 표절 의심 쌍만을 골라내어 좌우 비교 화면으로 즉시 보여줍니다."*

---

### Slide 7. 핵심 기술 3: Docker 격리 샌드박스 자동 채점 (Docker Sandbox)
* **슬라이드 내용**:
  * 다중 보안 플래그 적용:
    * `--network none`: 외부 네트워크 침투 및 사내망 유출 원천 차단
    * `--read-only`: 시스템 파일 변조 방지
    * `--pids-limit 64`: 무한 프로세스 생성(Fork Bomb) 공격 방어
    * `--memory 256m`: 서버 메모리 고갈 방어
  * Java 및 Python 다중 언어 테스트 케이스(공개/비공개) 자동 채점
* **발표 대본 (Script)**:
  > *"학생들이 낸 코드를 교수 연구실 PC에서 직접 돌리는 것은 보안상 매우 위험합니다. 악성 스크립트나 무한 루프가 있을 수 있기 때문입니다. SubmitHub는 코드가 제출되는 즉시 인터넷이 완전히 차단되고 루트 파일시스템 쓰기가 금지된 일회용 Docker 컨테이너를 띄워 채점하고 즉시 파기합니다. 호스트 서버는 100% 안전하게 보호됩니다."*

## 🎯 심사위원(교수님) 예상 질문 5선 & 완벽 방어 답변

### Q1. "기존 GitHub Classroom이나 대학 LMS가 이미 있는데, 굳이 SubmitHub를 만들어야 하는 차별점이 무엇인가요?"
* **답변**:
  > *"GitHub Classroom은 훌륭하지만 '학생이 피드백을 새 커밋에서 반영했는가'를 정량적으로 추적해 주지 않으며, 표절 검사나 샌드박스 채점 기능이 통합되어 있지 않아 교수가 외부 툴을 여러 개 조합해야 합니다. 기존 대학 LMS는 소스코드 단위의 파일 트리나 라인 피드백 자체가 불가능합니다. **SubmitHub는 '버전 관리 + 라인 리뷰 + 피드백 자동 추적 + 표절 검사 + 샌드박스 채점'을 단 하나의 웹 플랫폼으로 통합**했다는 점에서 독보적인 차별점을 가집니다."*

### Q2. "학생이 코드를 고치긴 했는데, 엉뚱하게 고쳐놓고 '반영됨'으로 판정받으면 어떻게 하나요?"
* **답변**:
  > *"좋은 지적입니다. SubmitHub는 이를 위해 2단계 방어 체계를 갖추고 있습니다. 첫째, 1차적으로 Myers Diff를 통해 해당 줄의 로직 변경 여부를 판단하고, 둘째, 필요시 Gemini LLM을 연동하여 코멘트의 의도와 학생 코드의 시맨틱 일치도를 분석합니다. 마지막으로 **교수 화면에 '수락(Accept)' 및 '무시(Reject)' 버튼을 제공**하여, 교수가 최종적으로 판정 결과를 검토하고 반려할 수 있도록 인간 개입(Human-in-the-loop) 설계를 적용했습니다."*

### Q3. "Docker 채점 환경에서 학생 코드가 시스템을 망가뜨리지 않는다고 어떻게 확신하나요?"
* **답변**:
  > *"SubmitHub의 `DockerCommands` 격리 엔진은 6단계 보안 설정을 강제합니다. `--network none`으로 네트워크를 원천 차단하여 외부 해킹이나 리버스 쉘을 방지하고, `--read-only`로 루트 파일시스템 수정을 막았으며, `--pids-limit 64`로 포크 폭탄을 차단했습니다. 또한 `--cap-drop ALL`과 `no-new-privileges`로 컨테이너 내부에서도 루트 권한 상승이 불가능하며, 학생 코드는 오직 읽기 전용으로만 마운트되므로 호스트 시스템은 완벽히 격리됩니다."*

### Q4. "표절 검사에서 학생들이 변수명이나 함수명만 교묘하게 바꾸면 어떻게 걸러내나요?"
* **답변**:
  > *"저희는 스탠포드 MOSS 논문에서 제안된 **Winnowing 알고리즘**을 직접 구현했습니다. 소스코드를 분석하기 전 Lexer 정규화를 거쳐 모든 변수명과 식별자를 일반 토큰으로 치환하고, 주석과 공백을 제거합니다. 그 후 k-gram 윈도우 해시를 추출하여 지문(Fingerprint)을 비교하기 때문에, 변수명을 바꾸거나 주석을 임의로 넣어도 지문 해시값이 동일하게 유지되어 100% 적발할 수 있습니다."*

### Q5. "대용량 프로젝트나 ZIP 파일을 올렸을 때의 성능이나 보안 문제는 없나요?"
* **답변**:
  > *"SubmitHub의 `UploadProcessor`는 디스크에 바로 풀지 않고 메모리 스트림 상에서 안전하게 파일을 추출하며, 경로 내에 `..`이나 절대 경로가 포함된 파일이 있을 경우 압축 해제를 즉시 거부하는 **Zip Slip 보안 취약점 방어 로직**이 내장되어 있습니다. 또한 파일당 5MB, 총 20MB, 최대 200개 파일로 제한을 두어 Zip 폭탄(Zip Bomb) 공격을 원천 방어합니다."*
