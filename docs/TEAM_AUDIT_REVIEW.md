## P1. 보안 (필수, 가장 먼저)

### P1-1. `/teams/{id}/audit` 권한 검사

- 위치: `web/TeamController.java` `auditTeam()`, `service/TeamAuditService.java` `auditTeam(Long, AppUser)`
- 문제: `currentUser` 를 받기만 하고 쓰지 않는다. 다른 강의 학생도 팀 ID 만 바꿔 넣으면 팀원 이름·학번·점수·피드백 현황을 볼 수 있다 (IDOR).
  `FeedbackService.computeUnchecked()` (권한 검사 없는 메서드)를 그대로 써서 남의 피드백 정보가 새어 나간다.
- 수정:
  - 허용: **해당 강의 담당 교수** 또는 **그 팀의 팀원**만. 그 외는 403 (기존 `AccessDeniedException` → 4xx 화면 흐름 사용).
  - 권한 검사는 서비스(`TeamAuditService.auditTeam`) 첫 줄에서 한다. 기존 `AccessService` 에 비슷한 검사(강의 교수 여부)가 있으면 재사용.
  - 학생이 보는 경우 다른 팀원의 **점수(score)는 숨긴다** (`null` 처리, 화면은 `-`). 기여율·제출 여부는 팀 투명성 목적이라 보여도 된다.
- 완료 기준: 다른 강의 학생 403, 같은 강의지만 다른 팀 학생 403, 팀원 200(점수 숨김), 담당 교수 200, 다른 교수 403.

### P1-2. 팀 가입 `POST /teams/{teamId}/join`

- 위치: `TeamService.joinTeam()`
- 문제: 학생이 그 강의를 수강하는지, 과제가 조별 과제(`teamProject=true`)인지, 마감이 지났는지 확인하지 않는다. 팀 ID 만 알면 남의 강의 팀에 들어갈 수 있다.
- 수정 (서비스에서 검사):
  1. 과제의 강의를 수강 중인 학생인지 (기존 `AccessService` 의 수강 검사 재사용)
  2. `assignment.isTeamProject()` 가 true 인지 → 아니면 `IllegalStateException("조별 과제가 아닙니다.")`
  3. 마감(지각 허용 기한 포함)이 지나지 않았는지
  4. 브랜치 이름 형식 검사: `^[A-Za-z0-9._/-]{1,100}$`, `..` 포함 금지
- 완료 기준: 위 4가지 각각 실패 테스트 + 정상 가입 테스트.

### P1-3. 팀 생성 `POST /assignments/{id}/teams`

- 위치: `TeamService.createTeam()`
- 문제: P1-2 와 같은 검사가 전혀 없다. 개인 과제에도 팀을 만들 수 있다.
- 수정: P1-2 의 1~4 와 동일 + 팀명 길이(1~100)·공백만 금지 + `repoUrl` 은 비어 있거나 `https://github.com/{owner}/{repo}` 형식만 허용 (기존 GitHub 제출 기능의 URL 파서 재사용).
- 컨트롤러 `CreateTeamForm` 에 `@Valid` 를 실제로 적용 (지금 `@NotBlank` 가 있지만 `@Valid` 가 없어 검사가 안 돈다).

## P2. 정합성

### P2-1. 브랜치를 실제로 확인한다 (최소한의 정직성)

- 문제: `branchName` 은 사용자가 입력한 글자일 뿐이다. 기여도는 각 학생의 "최신 제출물"로만 계산되고, 그 제출물이 팀 저장소의 그 브랜치에서 온 것인지 확인하지 않는다. 파일 업로드로 아무 코드나 내도 기여로 잡힌다.
- 수정:
  1. 조별 과제에서는 **GitHub 커밋 제출만 허용**하거나, 업로드 제출은 감사 화면에 `출처 미확인` 배지로 구분한다. (권장: 둘 다 허용하되 구분 표시)
  2. GitHub 제출일 때 제출의 저장소가 `team.repoUrl` 과 같고, 제출한 ref 가 그 팀원의 `branchName` 과 같은지 비교해서 감사 표에 `브랜치 일치 ✔ / 불일치 ✖ / 출처 미확인` 을 표시한다. (기존 GitHub 제출 기능이 저장한 저장소·ref·SHA 필드를 사용. 없는 필드는 추가하지 말고 보고)
  3. 불일치·미확인 제출은 기여율 계산에서 **제외하지 말고** 경고만 표시 (판단은 교수가).

### P2-2. 유효 코드 줄 계산

- 위치: `TeamAuditService.calculateValidCodeLines()`
- 문제:
  - `README.md`, `requirements.txt`, `*.yaml`, `*.json` 같은 문서·설정 파일도 코드 줄로 센다.
  - `*` 로 시작하는 줄을 전부 버려서 C 포인터 코드(`*p = 1;`)가 빠진다.
  - 블록 주석 안쪽 줄, 파이썬 docstring 은 못 거른다.
- 수정:
  - 소스 확장자만 센다: `.java .py .js .ts .c .h .cpp .hpp .cs .kt .go .rs .rb .php .html .css .sql` (목록은 상수 하나로).
  - 주석 제거는 직접 짜지 말고 **이미 있는 `core.similarity.CodeTokenizer` 를 재사용**: 토큰이 하나라도 있는 줄 수를 센다 (토큰의 `line` 값의 서로 다른 개수). 주석·공백 처리 규칙이 표절 검사와 같아져서 발표 때 설명도 일관된다.
- 완료 기준: README 만 있는 제출 = 0줄, `*p = 1;` 포함, `/* … */` 여러 줄 주석 제외, 파이썬 `"""docstring"""` 제외 테스트.

### P2-3. 배지 기준 통일

- 코드: 핵심 기여 `>= 45%` 이고 팀원 3명 이상일 때만. 명세서: `>= 40%`.
- 수정: 기준값을 설정(`submithub.team.lead-threshold=40`, `submithub.team.low-threshold=15`)으로 빼고, 명세서와 코드를 같은 값으로 맞춘다. 2명 팀에서 "핵심 기여"를 안 주는 이유가 있으면 명세서에 적는다.

### P2-4. 제출 0건일 때 기여율

- 문제: 팀 전체 유효 줄이 0이면 모든 팀원에게 `100/N %` 를 준다 (아무도 안 냈는데 25%씩 표시).
- 수정: 총합 0 이면 모두 `0%` 또는 `-` 로 표시. 반올림 때문에 합이 100이 안 되는 것은 화면에 "반올림으로 합이 100%가 아닐 수 있음" 한 줄.

### P2-5. 과제당 한 팀 보장

- 문제: "이미 다른 팀에 있음" 검사가 조회 후 저장이라, 동시에 두 팀에 가입하면 둘 다 성공할 수 있다. 최대 인원 검사도 같다.
- 수정: `team_members` 에 `assignment_id` 컬럼을 추가하고 `UNIQUE(assignment_id, student_id)` 제약. 위반 시 친절한 메시지. 최대 인원은 팀 행을 `PESSIMISTIC_WRITE` 로 잠근 뒤 검사.
- 완료 기준: 같은 학생이 두 팀에 동시 가입 시 하나만 성공하는 테스트 (기존 동시 제출 테스트 방식 참고).

### P2-6. 오류 처리

- `catch (Exception e)` → `IllegalArgumentException`, `IllegalStateException` 만 잡아 메시지 표시. 그 외는 공통 오류 처리로 넘긴다 (내부 메시지 노출 방지).
- 가입 실패 시 `/assignments` 가 아니라 원래 과제의 팀 목록으로 돌아가게 (팀이 없으면 홈).

## P3. 기여도 지표 (설계 보완)

지금 지표는 "각자 최신 제출물의 줄 수 비율"이다. 팀원이 같은 저장소의 전체 코드를 각자 내면 모두 비슷하게 나오고, 남의 코드를 내도 자기 기여가 된다.
**P3-A 는 필수**, P3-B 는 여유가 있을 때.

### P3-A. 화면·문서 표현 바로잡기 (필수, 코드 변경 작음)

- "객관적 기여도 감사" → **"제출 기반 참고 지표"** 로 표현을 바꾼다 (화면 제목 아래 안내문 + 명세서).
- 감사 표에 지표를 하나 더 둔다: **팀원 간 제출물 중복도** — 이미 있는 `SimilarityChecker` 로 팀원 최신 제출물끼리 비교해서 70% 이상 겹치면 `팀원 간 코드 중복` 경고. (같은 코드를 각자 낸 경우를 잡는다)
- 판정 문구 "무임승차 의심" 은 "활동 저조 — 확인 필요" 로 완화 (자동 판정으로 학생을 낙인찍지 않게).

### P3-B. 브랜치 실제 변경량 (선택)

- GitHub Compare API (`GET /repos/{owner}/{repo}/compare/{base}...{branch}`) 로 각 팀원 브랜치가 기준 브랜치(main) 대비 **추가·삭제한 줄 수, 커밋 수, 커밋 작성자** 를 가져와 표시.
- 기존 GitHub 클라이언트(토큰·요청 제한·오류 처리)를 재사용, 결과는 DB 에 캐시하고 "새로 고침" 버튼으로만 갱신.
- 커밋 작성자가 그 학생이 아닌 커밋 비율도 표시 (대신 커밋해 준 경우 탐지).
- 테스트는 가짜 GitHub 서버로 (기존 방식 그대로).

## P5. 명세서 정정 (`docs/SUBMITHUB_FEATURES.md`, `docs/TEAM_AUDIT_FEATURE.md`)

실제 코드와 다른 표현은 심사에서 바로 지적된다. 아래를 고친다 (코드에서 grep 으로 확인함).

| 명세서 표현 | 실제 | 고칠 표현 |
| --- | --- | --- |
| AST 표절 검사 | 구문 트리(AST)가 아니라 토큰 기반 | "토큰 기반 Winnowing 표절 검사" |
| MOSS 호환 | MOSS 와 같은 알고리즘 계열일 뿐 호환 아님 | "MOSS 와 같은 Winnowing 방식" |
| JGit | 사용 안 함 (GitHub REST API) | "GitHub REST API" |
| WebSocket, 실시간 스레드 | 사용 안 함 (일반 폼 전송) | "코멘트 스레드(답글)" |
| Optimistic Lock | `@Version` 없음. 버전 번호는 유니크 제약+재시도/잠금 방식 | 실제 방식으로 |
| 지각 감점 비율 설정 | 감점 기능 없음 (지각 허용 기한만) | 삭제 또는 "지각 허용 기한" |
| Git 버전 히스토리 + Myers Diff 로 기여도 감사 | 기여도 계산에 diff 사용 안 함 | P2·P3 반영 후 실제 방식으로 |
| 배지 기준 40% | 코드 45% (P2-3 에서 통일) | 통일된 값 |
| "완벽하게 지원", "킬러 기능" 등 | — | 과장 표현 삭제, 사실만 |

명세서는 **코드를 고친 뒤 마지막에** 실제 동작에 맞춰 고친다. 고친 뒤 각 표현을 코드에서 찾을 수 있는지 `파일:줄` 로 보고.
